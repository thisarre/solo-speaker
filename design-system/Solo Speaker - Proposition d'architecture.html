01

Architecture cible

Une architecture modulaire, orientée features. Le cœur du produit (talks, éditeur, IA, speaking) vit dans des modules isolés ; l'App Router ne fait qu'assembler. Tout rendu data passe par les Server Components ; les Server Actions remplacent une couche API classique.

Présentation
App Router — routes, layouts, Server Components pour le data-fetching, Client Components pour l'interactivité (éditeur, auto-scroll).
Features
Modules métier — auth, talks, editor, ai, speaking. Chacun expose composants, hooks, schémas (Zod) et accès données.
Données
Server Actions + Supabase — mutations typées côté serveur, RLS comme garde-fou de sécurité, jamais de clé service exposée au client.
IA
Route Handler streaming — un endpoint /api/ai/generate côté serveur appelle le LLM ; le client consomme le flux. La clé reste serveur.
Plateforme
Supabase — Auth (email + magic link), Postgres, RLS. Vercel pour l'hébergement.

Principes directeurs

  • Server-first. Lecture de données dans des Server Components, mutations via Server Actions. On n'ajoute un Client Component que là où l'interactivité l'exige.
  • Sécurité par RLS. Chaque ligne porte un user_id ; les policies Postgres garantissent qu'un utilisateur ne voit que ses Talks — même si une requête fuit.
  • L'IA est un service, pas une dépendance d'UI. Isolée derrière une interface (generateOutline(), expandSection()) ⇒ on peut changer de modèle sans toucher aux écrans.
  • Modules autoportants. Supprimer une feature = supprimer un dossier. Pas de couplage transversal caché.
Décision à valider

Fournisseur LLM pour la « Génération IA basique » : Claude (Anthropic) / OpenAI / Mistral. Je conçois l'interface AIProvider pour rester agnostique, mais le choix conditionne les SDK et les variables d'environnement.

Règle simple : un écran importe depuis features/* ; une feature n'importe jamais un écran. Les dépendances pointent toujours vers le bas.

Sécurité — Row Level Security

RLS activé sur les 3 tables. Policy type : user_id = auth.uid() pour talks, et talk_id IN (select id from talks where user_id = auth.uid()) pour talk_sections. Un trigger insère une ligne profiles à chaque signup.

Volontairement écarté de la V1 : versionnage des Talks, table ai_generations (historique des prompts), tags/dossiers. Faciles à ajouter plus tard sans casser ce socle.

Pages nécessaires

Sept écrans pour couvrir tout le parcours, de la connexion à la prise de parole.

/login · /signup
Authentification. Email + mot de passe et/ou magic link Supabase. Design épuré, pleine page, centré.

Création (dialog ou page). Titre, type, public, durée cible, langue → crée un brouillon puis ouvre l'éditeur.

Éditeur. Sections ordonnées, autosave, panneau IA latéral (générer un plan, développer une section). Bouton « Présenter ».
/talks/[id]/speak
Speaking Mode. Plein écran, fond sombre, gros texte, auto-scroll à vitesse réglable, play/pause, minuteur, progression.
/account
Compte (léger). Nom, rôle, langue par défaut, déconnexion. Minimal en V1.

Design system initial

Direction « Editorial Stage » : papier ivoire chaud, encre profonde, un seul accent ocre « projecteur ». Un serif éditorial pour la voix (titres de Talk), une grotesque nette pour l'interface. Premium, sobre, sans bruit.

Principes d'usage

  • Le serif sert la voix. Réservé aux titres de Talk et au texte du teleprompter — là où l'on lit « à haute voix ». Le reste est en grotesque.
  • Un seul accent. L'ocre « projecteur » signale l'action principale et l'IA. Jamais décoratif.
  • Le sombre est un mode, pas un thème. Le fond « Stage » est dédié au speaking mode (lisibilité scène) ; l'appli reste sur papier ivoire.
  • Rayons & espace. Coins 10–16px, hairlines à 1px, beaucoup de blanc. Densité maîtrisée, zéro ombre lourde.

08

À récupérer (ou non) de l'ancien projet

Bloquant pour être précis

L'« ancien projet » n'est pas attaché ici. Lie-le (codebase, repo, ou capture d'écran via le menu Import) et je transforme la grille ci-dessous en liste exacte fichier par fichier. En attendant, voici le principe.

À récupérer

  • Config Supabase (URL, schéma, migrations encore valides)
  • Prompts IA qui fonctionnent déjà bien
  • Logique métier éprouvée (estimation de durée, parsing de plan)
  • Contenus / Talks réels pour tester avec de vraies données
  • Tokens de marque s'ils existent (logo, couleur signature)

À laisser

  • Tout code lié aux features hors V1 (workspace, Stripe, RAG, analytics, PWA)
  • Ancienne structure de dossiers si non modulaire
  • Dépendances UI obsolètes / composants ad hoc
  • Tables DB des features écartées
  • Dette technique & contournements — on repart propre

Approche recommandée : nouveau dépôt propre bâti sur cette architecture, dans lequel on réimporte sélectivement ce qui a de la valeur — plutôt qu'un refactor de l'existant.

Cette proposition est volontairement cadrée sur le MVP V1 : mono-utilisateur, sans workspace, Stripe, RAG, analytics ni PWA. Chaque écart est listé pour qu'on décide ensemble avant de coder.
