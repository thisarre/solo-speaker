## 2. Le bug : quota STT contournable (`/api/deepgram/token`)

**Sévérité : moyenne-haute. Pas une fuite de données — une fuite d'argent.**

### Le mécanisme

Avant de frapper un token Deepgram, la route vérifiait si une session existait déjà, pour ne pas
réserver deux fois sur un re-mint légitime :

```
.from("stt_sessions").select("id").eq("id", sessionId).maybeSingle()
```

Deux trous dans cette requête : **aucun filtre sur `user_id`**, et **aucun filtre sur `status`**.
Or `sessionId` vient du client. La simple *existence* d'une ligne suffisait à sauter à la fois
l'insertion de la réservation **et** l'incrément de `usage_counters`.

### L'exploitation

1. Session normale avec `sessionId = S` → réservation écrite, token frappé.
2. Arrêt → `confirm_stt_session(S)` → `status = 'confirmed'`, réservation relâchée.
3. Rejeu d'un POST forgé avec **le même `S`** → la ligne existe → token frappé, **zéro
   réservation, zéro compteur**.
4. Le `confirm` suivant voit `status = 'confirmed'` → idempotent → **zéro seconde facturée**.
5. Boucle. Le cap n'avance jamais.

Même effet avec un `sessionId` passé au statut `expired` par le cron `stt-sweep`, et avec le
`sessionId` d'un autre compte (pas de filtre `user_id`).

### L'impact

- Le cap essai (15 min), Studio (60), Pro/Team (90) devient **décoratif** pour qui sait envoyer
  un POST. Un compte d'essai gratuit suffit.
- Coût Deepgram variable, non plafonné, non attribué. C'est exactement le risque §8.2 de
  `BUSINESS_REVIEW.md` (« surveille la marge par utilisateur »).
- `usage_counters` ne reflète plus l'usage réel → toute décision prise sur ces chiffres est fausse.

### Le correctif appliqué

Dans `src/app/api/deepgram/token/route.ts` : la requête sélectionne maintenant `user_id, status`,
et deux gardes ont été ajoutées avant la frappe du token — `403` si la session appartient à
quelqu'un d'autre, `409` si elle n'est plus `reserved`.

**Pourquoi ça ne casse rien** : le client honnête (`deepgram-provider.ts` ligne 159) tire un
`crypto.randomUUID()` neuf par session et remet la ref à `null` après confirmation. Il ne peut
donc structurellement pas atteindre ces deux refus. Seuls les rejeux forgés les touchent.
